# 小熙 Hushlight 项目总览

> 文档版本：V0.3
> 更新日期：2026-08-11
> 项目阶段：K0 立项；PRD 与 H0 硬件方向已通过，技术方案待评审
> GitHub 仓库：`cafelemon/hushlight`

## 1. 项目定义

小熙是面向成年用户的桌面 AI 情绪陪伴伙伴。她先判断用户当下更需要聊天、安静、音乐、轻提醒还是一个明确动作，再以克制、可退出的方式响应。

小熙不是给工作助手增加情绪话术，也不是只会聊天的硬件。完整产品由四部分组成：

- 桌面设备：用户交流入口和物理存在感。
- 云端服务：实时语音、对话、情绪与需求判断、记忆和策略。
- Web 控制台：账户、设备、角色、模式、记忆、权限、订阅和诊断的大本营。
- PC Bridge：本地执行器，连接音乐、系统设置、提醒和受支持的本地应用。

## 2. 一句话定位

> 小熙是一个懂得陪你、也能在你需要时替你做一件小事的桌面 AI 伙伴。

## 3. 核心用户价值

| 价值 | 用户感知 |
|---|---|
| 陪伴 | 想聊时有人回应，不想聊时不会被追问 |
| 状态理解 | 不只识别“高兴/难过”，还判断用户想被听见还是想解决问题 |
| 环境调节 | 根据明确请求或克制建议播放音乐、调整音量、启动休息计时 |
| 轻行动 | 用户明确提出后，打开内容、记录提醒或准备聊天消息 |
| 长期关系 | 记得用户确认过的偏好、边界和重要事项 |
| 低操作负担 | 一次安装和授权后，日常主要通过语音完成 |

## 4. 当前产品判断

### 已确认

- 产品代号为“小熙”，仓库名为 `hushlight`。
- 陪伴是产品本体，本地行动是增强价值。
- PC Bridge 对丰富能力有必要，但必须完成消费级产品化。
- Web 控制台是统一配置与管理入口。
- 首版优先音乐、音量、提醒、打开内容和消息草稿/确认发送。
- V0 采用 macOS、Windows 双线并行开发，分别由不同开发者负责。
- 首个音乐适配对象为网易云音乐，首个聊天适配对象为微信。
- 关系与偏好记忆以云端为权威，Bridge 保存运行所需缓存。
- V0 制作两台 H0 内部研发样机，分别供 macOS、Windows 开发线联调；不作为种子用户交付物。
- H0 采用两条并行硬件线：两台 Korvo-2 参考设备保障软件立即开发；硬件工程师同步落实自研 PCB、3D 打印结构和双轴云台。
- 产品形态为固定底座与双轴轻量头部，运动件仅为屏幕、摄像头及必要支架；待机不跟随，主动唤醒和对话期间才启用端侧定位与跟随。
- 自研工程板通过切换 Gate 后成为 macOS、Windows 软件开发主设备；Korvo-2 保留为参考、回归和延期兜底。
- H0 以角色面孔、本地动画和有语义的双轴身体语言增强陪伴表现，不在设备屏幕展示工具日志和长文本。
- 消费版千台级 BOM 先按不高于 150 元评估；299 元日常价、249 元活动价仅为立项价格目标。
- 多款前端视觉风格不是 V0 必选项。
- 用户对丰富功能的直接感知高于对复杂隐私架构的主动需求，但最小权限、可见状态和高风险确认仍是发布底线。

### 竞品事实

- 用户向竞品客服确认：本地控制能力需要安装 PC 端程序，目前通过压缩包而非应用商店交付。
- 客服确认竞品存在主动关怀和月卡收费。
- 客服声称记忆采用本地存储；效果和数据行为尚未实机验证。
- 视频显示竞品通过 `macos_automator MCP Server`、Automation/Accessibility 权限和本地工具控制网易云、抖音、微信、亮度与音量。

### 关键推断

- 竞品已经证明“语音控制本地软件”具有传播力，但尚未证明具备稳定、低门槛的消费级交付。
- 小熙的差异化不是展示更多命令，而是将安装、授权、确认、失败处理、升级和诊断做成完整体验。

## 5. V0 目标

V0 验证一个命题：

> 用户是否会因为“自然陪伴 + 音乐/环境调节 + 明确请求后的轻行动”，持续使用小熙，并认为她比纯聊天应用更有存在感、比粗糙自动化工具更容易使用。

V0 必须形成以下闭环：

```text
用户自然表达
→ 小熙判断互动需要
→ 聊天 / 安静 / 音乐建议 / 明确动作
→ 必要时调用 PC Bridge
→ 展示或播报结果
→ 用户接受、纠正、撤销或退出
→ 更新已授权偏好
```

## 6. V0 范围

### 包含

- 语音聊天和自然打断。
- 情绪、需求、置信度和回应策略结构化输出。
- 陪聊、安静陪伴、音乐调节三种主要策略。
- Web 账户、设备绑定、模式、记忆、权限和 Bridge 下载入口。
- 有最小 GUI/托盘壳的 PC Bridge，不出现命令行安装流程。
- 音乐播放控制、系统音量、提醒计时、打开内容。
- 一个聊天软件的消息草稿和确认发送验证。
- 基础主动关怀、静默时段和频率预算。
- 操作结果、失败原因和最近记录可见。
- 两台 Korvo-2 参考设备，以及通过切换 Gate 后至少 3 块同版本自研工程板，用于硬件在环、双轴表现和 Bridge 协作验证。

### 不包含

- IDE、Git、构建状态和复杂办公自动化。
- 任意 Shell、文件批量删除、支付和生产系统操作。
- 儿童、老人照护、心理诊断和虚拟恋人定位。
- 摄像头持续分析。
- 多平台、多音乐软件和多聊天软件同时适配。
- 多套独立前端代码和角色商城。
- 开模、认证和量产承诺。

## 7. 成功条件

| 维度 | V0 判断标准 |
|---|---|
| 陪伴价值 | 种子用户能够区分小熙与普通聊天应用，并愿意继续使用 |
| 行动价值 | 音乐和轻行动不需要学习命令，用户能自然说出需求 |
| 安装体验 | 普通用户不接触命令行即可完成 Bridge 安装、绑定和授权 |
| 安全底线 | 未确认的对外消息发送数为 0；禁止动作执行数为 0 |
| 稳定性 | Bridge 离线或工具失败时，小熙明确降级，不伪造成功 |
| 成本 | 形成真实语音轮次、模型、存储和本地适配维护成本记录 |

详细通过条件见 [04_acceptance_checklist.md](04_acceptance_checklist.md)。

## 8. 主要风险

| 风险 | 早期信号 | 处理方向 |
|---|---|---|
| 陪伴退化为工具演示 | 用户只在展示时调用命令 | 以日常聊天、音乐和主动关怀为主旅程 |
| Bridge 安装阻力 | 下载后未安装或未授权 | 一键安装、权限引导、失败自检 |
| UI 自动化脆弱 | 软件更新后动作失败 | 适配器隔离、版本检测、失败即停止 |
| 对话成本高 | 重度用户成本接近月卡收入 | 模型分层、短回复、本地动作不调用高价模型 |
| 主动关怀打扰 | 用户连续忽略或关闭 | 主动预算、静默时段和自动降频 |
| 消息误发送 | 人名或内容识别错误 | 草稿、对象与内容复述、发送前确认 |
| 记忆误用 | 用户纠正或删除后仍被引用 | 来源、修改、删除和引用追踪 |
| 跟随抖动或无意义运动 | 头部频繁微调、持续找人或撞限位 | 大死区、意图滤波、轨迹规划、有限搜索和安全停机 |
| 视觉隐私不可信 | 待机仍采集或用户无法判断摄像头状态 | 待机硬关闭、可见工作指示、物理遮挡和端侧处理 |
| 运动破坏语音体验 | 电机噪声或振动导致误唤醒、AEC 下降 | 固定音频底座、电源隔离、运动与聆听时序仲裁 |
| 自研硬件拖延软件 | 首板、结构或云台延期使两端停工 | Korvo-2 参考设备先行、统一 BSP、独立切换 Gate |
