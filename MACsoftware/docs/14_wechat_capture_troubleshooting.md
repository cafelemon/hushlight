## 已证实的环境与事实

- macOS26.7.1（25G241），arm64。
- 原路径`/Applications/WeChat.app`为4.1.13，腾讯Developer ID签名，Team ID `5A4RE8SF68`。
- 另有`/Applications/WeChat 2.app`为4.1.15，Mac App Store签名且Team ID相同，完整签名校验通过。
- 用户正常退出旧版后已启动并登录4.1.15，当前运行路径为后者；原版未替换、未重签，没有同时运行两个版本。
- 实验宿主的屏幕捕获与AX预检都通过；设置页可返回非空图像，聊天页在CUA中空白。不要再次把此情形默认归为TCC缺失。
- Core Graphics公开元数据：4.1.13主聊天窗/文件传输助手独立窗为`sharing_state=0`，设置页为`1`；4.1.15的主窗和测试独立窗仍为`0`。
- Apple将`CGWindowSharingType.none`定义为窗口不共享。此证据证明标记存在，不证明是谁/何时设置，也不证明微信或系统的内部策略原因。

## 实际做过什么

按用户要求先试Gist的运行流更新过滤器，再按新增专项报告做独立Swift矩阵。没有执行Gist的临时副本重签、LLDB、取钥、SQLCipher或发送流程。

| 实验 | 实测 |
|---|---|
| A SCScreenshotManager单窗 | 主窗图像全透明，固定测试串未匹配 |
| B SCStream单窗 | 主窗不透明黑帧，固定测试串未匹配 |
| C 限定目标的应用流 | 有限等待内无帧 |
| D 应用流启动后切目标窗 | 过滤器已调用更新，更新后没有帧，不是因为warmup无帧而提前停止 |
| D2 设置窗预热后切主窗 | 3次均有设置预热帧和更新后的新帧，但新帧仍纯黑；不是旧帧/时间戳过滤假象 |
| E 显示器过滤、裁在目标几何 | 用户明确同意后执行；有图像和OCR，固定测试串未匹配，不算成功 |
| F AX | 主窗仅6节点，无固定测试正文 |
| G 设置页 | 原型可返回25行OCR、非空像素；与CUA设置页可见的事实一致 |

诊断中确认共享标记为none后，停止进一步穿透尝试。原型新增明确阻止此类窗口捕获的保护；元数据I模式仍可复查。真实消息未发送，真实聊天图片/正文未落盘或上传；日志只保存环境、窗口身份、像素/帧计数和固定测试串匹配布尔。

## 如何重查，避免以后重复折腾

1. 先明确运行路径、版本、PID。两个相同Bundle ID的App会让工具按Bundle ID选App发生歧义，必须固定路径；磁盘存在副本不等于双进程，也不证明白屏由此引起。
2. 正常显示无敏感信息的测试窗口；先运行元数据诊断，不先申请或重置权限。
3. 若目标共享标记为0，报告“窗口不共享”，停止把重新申请屏幕录制当成修复。
4. 若标记不是0且权限正常，再用独立A–G矩阵核对固定测试串；像素非白、OCR有行数或API返回成功都不等于读到正确正文。
5. 如果未来官方版本或用户可见设置能恢复共享，必须复查标记，并实际读到固定测试串、多次重复和窗口切换后稳定，才能关闭该问题。

```sh
xcrun swiftc -parse-as-library MACsoftware/experiments/wechat-capture/CaptureTest.swift -o /tmp/orbit-wechat-capture-matrix
/tmp/orbit-wechat-capture-matrix --mode I --target 文件传输助手
```

不要运行读库、重签或注入流程来“验证权限”。不删除账号数据、不重置TCC、不关闭SIP。用户已授权权限修改，但目前没有发现可通过公开权限开关解除此窗口标记的方法；没有实施无证据的权限重置。

## Orbit改动及未完成部分

Orbit捕获服务对微信同ID/PID且明确不共享的窗口返回`sharingRestricted`；页面区分窗口共享限制与缺少系统权限。这个改动是停止无效重试、保留准确结果，不是解除微信限制。QQ捕获不受这条微信专属判断影响。生产截图API未改为实验动态流，没有集成无效实验路线。

尚无可证实的正文恢复方法。下一步只评估官方支持的共享方式或用户主动提供无敏感文字的协作入口，不把绕过已确认的限制作为默认产品能力。既有明确授权的单聊问候+收到回复后答一次仍未执行；恢复可核实观察后再继续，不把历史授权当作可盲发的依据。
